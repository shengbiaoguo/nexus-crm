# Nexus CRM — 需求规格说明书

- 版本：V0.7（需求基线草案；DC-001/008/009/011/012 文档修订）
- 日期：2026-10-29
- 状态：业务核心原则已确认；补充规则为架构暂定，待真实业务验证
- 场景：35 人左右的 B2B 技术服务公司，主营官网、定制软件、设计、咨询；内部员工使用。

## 1. 目标与边界

替代分散的 Excel/聊天记录，建立客户→商机→报价→订单→交付→收款的可追溯业务链，支持精确权限、流程审批、报表、操作审计。

### V1（P0）
登录与人员/角色权限、客户与联系人、商机、服务目录、报价及版本、订单及审批、交付项目及验收、收款登记/确认/冲正、订单取消与终止、操作审计、基础报表。

### V1.1（P1）
提醒通知、客户跟进日程、更多经营统计、导出。

### 不纳入 V1
多租户、在线支付/银行直连、总账和税务核算、库存、复杂 BPM 工作流设计器、移动应用、微服务。

## 2. 角色

- 系统管理员：账户、角色和基础配置；默认不因拥有系统管理权而获得财务审批权。
- 销售：管理被授权客户和商机、报价、订单草稿，提交审批/取消/终止申请。
- 销售经理：团队客户管理、报价/订单审批、取消审批（按授权范围）。
- 交付成员：执行分配的交付任务、提交交付物。
- 交付经理：交付启动、分配、验收审核、结项建议、终止工作量评估。
- 财务：收款核对/确认、冲正/退款处理与应收查询。
- 业务负责人：跨部门例外审批、重大终止审批、启动首付款豁免。

角色只是默认权限包；服务端还必须执行数据范围和对象级权限校验。申请人不得审批自己的申请（V1暂定）。

## 3. 已确认核心业务规则（BR-001—BR-010）

- BR-001 客户有一个主负责人，可以设置多名协作销售。
- BR-002 一个客户允许多个独立商机。
- BR-003 报价修改保留完整版本和修改历史。
- BR-004 一个订单允许多笔收款。
- BR-005 已确认订单金额变化需走订单变更审批，不得直接编辑。
- BR-006 企业信用代码用于精确去重；缺失时按名称、联系方式提示疑似重复并人工核实。
- BR-007 根据客户已接受的报价版本生成订单草稿，之后才确认正式订单。
- BR-008 首付款经过财务确认后方可启动交付，业务负责人可以审批豁免并留痕。
- BR-009 已确认错误收款以冲正方式纠正，不得物理删除。
- BR-010 离职员工停用登录并使会话失效，历史身份保留；客户和商机可经授权批量移交。

## 4. 订单状态和核心流程（架构暂定）

订单状态：DRAFT, PENDING, CONFIRMED, COMPLETED, CANCELLED, TERMINATED。

| 起点 | 命令 | 终点 | 关键前置条件 |
|---|---|---|---|
| DRAFT | submit | PENDING | 订单内容完整，引用有效报价版本及客户交易条款接受依据，生成不可变审批快照 |
| PENDING | approve | CONFIRMED | 有审批权限、审批快照未过期，满足职责分离，版本校验成功 |
| PENDING | reject | DRAFT | 留存拒绝原因和审批历史；重新提交生成新快照 |
| PENDING | withdraw | DRAFT | 由有权人员撤回且未形成审批决定 |
| CONFIRMED | approve cancellation | CANCELLED | 交付从未启动；取消方案及财务处置已批准 |
| CONFIRMED | approve termination | TERMINATED | 交付已启动；结算方案经交付、财务及业务负责人授权确认 |
| CONFIRMED | complete | COMPLETED | 现行已生效交付范围全部验收，且无阻断性待处理业务申请 |

DRAFT 作废的最终状态以及从 PENDING 直接作废暂不确定，初期可禁止；订单终态不能通过普通更新恢复。业务完成不要求尾款结清。

财务状态（应收/已收/退款）及交付状态（未启动/执行中/待验收/已验收/暂停）独立于订单主状态，不使用 DELIVERING 作为订单状态。

## 5. 关键不变量与一致性规则（架构暂定）

### INV-004 交付启动与订单取消互斥
交付曾启动的订单不可进入普通取消流程；只能按终止流程处理。取消待审期间禁止启动交付。两命令以同一 orders 行为锁定锚点：在同一 MySQL 事务中先锁定订单行（或执行条件更新并提升 version），随后核查相关取消申请及交付状态，再写各自业务记录并提交。两个命令都必须遵守相同锁定顺序和协议；禁止仅依赖前置 SELECT。订单保持 CONFIRMED，而 DeliveryProject 独立变为 IN_PROGRESS。冲突不能伪造为审批人主动驳回，需记录申请失效或冲突尝试。关键尝试在业务事务前独立持久化 STARTED，成功状态及成功审计随业务事务提交，确定回滚后独立记录 FAILED；崩溃或提交不明保留 UNKNOWN 待核对，不伪造失败。预写失败不执行业务，后续失败记录写入故障返回 503 并告警，详见 ADR-003。

### INV-005 订单完成
交付验收以当前已生效的交付范围版本为准，所有必需交付项均有有效验收凭据。不得存在阻断性的待决取消、终止、重大变更申请。完成订单与变更生效都锁定同一个 orders 行，并在事务内重查当前交付范围版本和有效验收，不允许先查询后无保护写入。已经完成订单的新需求须走新订单或另经明确约定的补充服务流程，不自动回退历史终态。

### INV-006 审批并发与请求幂等
同一审批轮次只允许一个决定：审批表决和订单状态在同一事务中写入，使用版本/状态条件或行锁。V1 Idempotency-Key 在同一不可变用户 ID 作用域内跨命令唯一；操作、目标及规范化请求体进入指纹，同键不同操作/目标/参数返回 409。幂等执行结果和业务提交在同一 MySQL 原子事务中落库。并发同键受控等待最多 2 秒，未完成返回 409 及 Retry-After: 1，不二次执行。成功重试先检查当前授权再回放首次结果，不因旧业务版本拒绝有效重放；不同 key 的新命令重新检查状态。V1 不缓存失败，回滚同时释放 Key；提交不明先用原 Key 核对，无法确定返回 503，禁止换 Key 自动重做。成功结果技术默认至少保留 7 天，过期清理后不保证重放或识别旧 Key，客户端不得复用，未知结果须查询核对；详见替代 ADR-002 的 ADR-005。

## 6. 模块和实体（概念层，非最终表设计）

DC-001 技术基线详见 permission-matrix.md V0.2 §4、§8：销售子资源按当前客户继承；商机负责人/创建者不单独授予访问权；TEAM 按当前客户负责人部门及下属部门；交付/财务仅必要投影。角色动作与范围成对求值，不跨角色拼接。业务角色配置及授予另需受保护的 role:grant_business，禁止管理员或业务负责人自授。每次请求检查权威账号及权限；写入事务内重验，撤销与在途操作按共同锁顺序线性化。以上是固定 Policy 的技术设计决定，不新增或更改 BR-001～010。未知审批门槛及复核依据未确定前默认拒绝，不以管理员放行。

## 8. API 契约与错误处理原则

- REST `/api/v1/...`；DTO 参数校验，未知字段处理策略统一。
- 正常响应使用 HTTP 语义：200、201、204；列表返回 `data` 和 `meta`；错误结构包含 `code/message/details/requestId`。
- 权限区分 401 未登录、403 无权，404 可用于避免越权泄露对象存在性；非法状态/版本冲突可返回 409；字段校验返回 400 或 422，项目内保持一致。
- 关键命令采用明确动作端点而非自由 PATCH status：提交、批准、拒绝、取消、终止、结项、收款确认、冲正。
- 审批、取消、终止、收款确认等操作保留事件与审计链；审计中避免泄漏凭证和敏感个人数据。

## 9. 数据、安全和运维非功能要求

- NestJS + TypeScript；MySQL + Prisma Migration；Redis 用于辅助缓存/限流，不作为资金、审批唯一事实源。
- 配置分环境；生产不得运行破坏性 schema 同步。迁移 SQL 进入版本库并评审；生产部署前完成备份/恢复验证及向后兼容评估。
- 服务端 RBAC + 数据级访问范围；安全密码存储；短期访问凭证、可撤销的刷新会话；账号停用后及时撤销可用会话。
- 日志结构化、含 requestId；关键业务审计与技术日志分离；不记录密码、Token、敏感全文。
- 核心事务、不变量、权限、重复请求有自动化集成测试；并发测试使用真实 MySQL，而不仅是 Mock。
- Docker Compose/Nginx 部署；HTTPS、备份策略、恢复演练和部署回滚步骤需文档化。
- 量化的性能、可用性、RPO/RTO 目标尚未由业务方确认；避免凭空承诺 SLA。

## 10. 验收场景（摘要）

1. 被授权销售创建客户→商机→报价多个版本→接受报价→订单草稿→经理确认，历史报价和审批快照不被覆盖。
2. 两名经理并发相反审批仅一项有效提交，另一项得到确定冲突响应。
3. 订单取消审批与交付启动并发，任何提交结果都不能造成“已取消且交付曾启动”。
4. 按首付条件控制交付启动；豁免需要授权、原因、审计。
5. 已验收当前全部有效交付义务且无阻断申请时可以完成订单，即使尾款未结清。
6. 收款重复提交不会产生重复入账；确认后纠错通过冲正而非删除。
7. 普通销售不得读取其他团队无授权客户；离职后其账户不能继续使用有效会话访问。
8. 订单变更需审批并原子更新合同版本及未结清的付款安排。

### 14.1 D-06 身份与去重

### 14.1.1 已批准方案：格式与归一化

V1 企业客户允许暂缺信用代码。`creditCode` 有值时采用以下**本产品录入格式**，不把它宣称为登记机关的真实性验证或完整国家标准校验：

1. 限制原输入最多 64 个 Unicode 码点，执行 Unicode NFKC，再去掉首尾 Unicode 空白，ASCII 小写转大写。
2. 结果必须匹配 `[0-9A-Z]{18}`，不能有内部空白、连字符或其他标点；不自动删除这些字符，以免把误输入悄悄变成另一身份。
3. 缺失或显式 `null` 表示尚未知晓；空串、纯空白是输入错误，不存成空串，也不将空串静默变为缺失。
4. 数据库只存归一化后的 `creditCode`，不另存未规范化副本。V1 不计算校验位、不联网验真；格式通过不代表企业真实、代码合法或已经核验。后续如需严格校验位/登记信息核验，应单独明确规则和历史数据兼容方案。
5. 创建时可缺失；后续允许有 `customer:update` 的人员补录或纠正，必须带 `expectedVersion` 并成功审计。**已有非空代码不能清空为 null**，防止释放身份后重新创建重复客户；纠错可直接替换为另一未占用代码。误建且无法纠正的记录暂走人工核实，V1 不提供释放/合并捷径。

归一化与提示键规定：

| 字段         | 规则                                                                                                           | 匹配方式                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 客户显示名称 | NFKC、首尾去空白、连续内部空白折为一个 ASCII 空格；保留大小写、括号、标点、地区和公司后缀                      | `normalizedName` 在显示名称基础上对 ASCII 字母大写；不去“有限公司”等后缀、不转拼音             |
| 联系人电话   | NFKC、首尾去空白；显示值限数字、`+`、空格、`-`、括号，`+` 仅可在首位；去格式符后为可选首位 `+` 加 3～20 位数字 | 存 `phoneNormalized`；不自动加/删国家区号，不把 `+86…` 与本地号码自动视为相同；V1 不收分机文本 |
| 联系人邮箱   | 首尾去空白、常规邮箱格式校验，V1 限 ASCII 邮箱，最长 254；保留显示值                                           | `emailNormalized` 全部 ASCII 小写；不删除 `+tag` 或点，不推断企业归属；仅提示，非唯一身份      |

名称与提示键比较仍使用项目约定的 `utf8mb4_0900_ai_ci`，因此大小写及重音等价按该 collation 处理；这只是提示，不形成名称唯一约束。测试须覆盖数据库比较与应用归一化的一致性。代码归一化先于请求指纹计算。

### 14.1.2 已批准方案：重复判断与提示流程

**硬重复**：非空归一化信用代码已被任一客户占用，创建或修改拒绝。客户归档后仍占用；不能用归档绕过唯一性。名称不参与硬重复判断。

**疑似重复**：当当前录入尚无信用代码时，对当前用户具有 `customer:read` 权限的数据范围执行以下 OR 匹配：规范化完整名称相同，或任一有效联系人的电话提示键相同，或邮箱提示键相同。不要求名称和联系方式同时命中，不用包含查询、编辑距离、分词或打分；命中按原因显示，不给相似度百分比。有信用代码但无硬冲突时，不因同名/同联系方式阻止录入。

新增只读语义的 `POST /customers/duplicate-check`，避免在 URL 中传联系人信息。请求 `{name, creditCode?, phone?, email?, excludeCustomerId?}`；phone/email 为正在人工核实的联系方式，不自动写入客户。客户创建仍只创建 Customer，联系人通过既有子路由新增。`excludeCustomerId` 仅限当前可读客户，否则 404。接口不预留代码、不保证随后创建成功。

- 必须有 `customer:read`；无该动作权限返回 403，不以 `customer:create` 推导读取资格。创建权限本身不要求额外读取权限，故仅创建授权的用户可录入但不能获得候选信息。
- 返回 `{candidates:[{id,name,status,matchReasons}],hasMore}`，最多 5 个，按 `id` 升序；候选和 `hasMore` 都只基于当前可见范围。信用代码有值时只查当前可见的代码精确冲突，原因 `CREDIT_CODE`；无代码时原因是 `NAME`、`PHONE`、`EMAIL`。
- 不返回联系人姓名、电话、邮箱、owner、团队、隐藏记录计数或全库 `exists`。不可见匹配与无匹配均返回空候选及 `hasMore:false`，不额外给“其他团队存在重复”的提示。
- 返回候选后由销售判断：已有同一企业则使用该客户；确为不同企业可继续创建。V1 不设“查重已通过”令牌、确认弹窗提交字段或审批表，不把读提示结果作为创建前置条件；读权限不足时请有权经理协助核实，不扩大销售读取范围。
- 硬冲突后无覆盖/强制创建选项；由具有相应范围的销售经理或业务负责人核实，复用已有客户或按既有受控分配流程处理。没有合并 API，也不自动转移责任人。D-07 的交接规则仍待其独立决定。
- 两个无代码请求即使命中同名/同联系方式，仍允许产生两条；这是 BR-006 的人工核实模式，不承诺无代码客户全库唯一。后续给两条补同一代码时只允许一条成功。

### 14.1.3 已批准方案：不可见客户响应与安全边界

全库代码冲突一律采用 `409 BUSINESS_RULE_VIOLATION`，固定消息“该客户信息无法保存，请核对企业信用代码或联系有权负责人处理”，不区分冲突对象可见性，不附目标 ID、名称、负责人、版本、命中数量或输入代码。可见客户的具体候选只能从独立、受范围限制的查询获取。不存在/不可见对象及错误父子路径均为 404；无动作权限为 403。

**明确的安全取舍**：全库唯一约束会使有创建权限的人从保存成功/409 中推断某个输入代码可能已被占用。统一错误能避免披露客户详情，但不能消除这一个占用信号；不能宣称“完全不泄漏存在性”。业务负责人已接受该最小信号，并限制接口为内部授权员工，复用部署限流和安全监测，不提供匿名或批量代码探测接口。若要求连占用信号也完全隐藏，需要异步受理/人工审核等不同产品流程，不作为本次默认方案。

联系人和查重输入不进入技术日志或幂等快照；查重 POST 不持久化候选请求、也不写成功业务审计。查重响应采用 `Cache-Control: no-store`；写审计只保留白名单元数据和变更字段名，不复制联系方式全文。

### 14.1.4 已批准方案：数据库唯一性和并发

- `customers.credit_code` 可空、全库 UNIQUE；多个 SQL NULL 合法。名称、电话、邮箱不设唯一。归档不释放代码。
- 预查只是用户体验；最终以真实 MySQL 唯一约束判定。不同 Key、不同用户同时创建相同规范化代码，至多一条提交，竞争失败转上述统一 409，禁止原样输出 Prisma/SQL 错误。
- 同 Key 同指纹沿用 ADR-005/T03，最多一次创建并返回相同真实 ID；业务、成功审计、幂等结果、attempt 成功原子提交。事务失败不残留客户或成功审计；提交未知按原 Key 核对，不换 Key 自动重做。
- 更新先依共同授权锁协议锁客户，重验权限/版本；代码补录/纠正仍受 UNIQUE 约束。同客户两个版本竞争只能一个成功；跨客户同代码竞争最终只能一个成功。


### 14.2 D-08 字段与行为

### 14.2.1 已批准方案：通用字段与 DTO 规则

以下表格定义已批准的业务契约，**不是 Prisma Schema**。长度单位为 Unicode 码点，实施 DTO 与 MySQL 字符列须一致，不以 UTF-16 code unit 截断；邮箱/代码/ID 等 ASCII 字段按其格式约束。短文本 NFKC 后去首尾空白；content、description、reason 只做换行统一和首尾空白处理，不重写正文字符。所有字符串拒绝 NUL 和不允许的控制字符；正文允许换行/制表符，以纯文本输出。

- 可编辑非空文本不接收空串或纯空白；可空文本用 `null` 清除。POST 可选字段缺失按表中默认；PATCH 缺失保持原值，显式 null 只对可空字段有效；不隐式转换数字/布尔值/数组，不接受未知字段。
- Customer、Contact、Opportunity 共用：`id` 服务端 BIGINT UNSIGNED（API 十进制字符串）；`version` UNSIGNED INT 默认 1；`createdAt/updatedAt` UTC DATETIME(3)；`createdBy` 历史 User FK。这些为服务端字段；成功实体更新提升其 version。FollowUp 无编辑，只有 `id/createdAt/authorId`，不为其添加无用途的 version/updatedAt。
- 所有 FK 保留 RESTRICT；无客户/商机/跟进物理删除端点。创建和动作命令采用既有 Idempotency-Key；PATCH 带目标实体 `expectedVersion`，统一经过幂等命令组件，结果仅 `{id,version,status?或stage?}` 标量摘要。
- 列表默认 page=1/pageSize=20，pageSize 1～100；稳定排序 `createdAt DESC,id DESC`，无动作权限 403，where 与 total 同一授权快照。查重接口使用前述独立排序。筛选白名单限各实体明确的父 ID、状态/阶段及 ownerId；owner 筛选始终与授权范围取交集。

### 14.2.2 Customer 最小字段与生命周期

| 字段           | 类型 / 长度           | 创建规则、默认与更新                                       |
| -------------- | --------------------- | ---------------------------------------------------------- |
| name           | 非空字符串 1～200     | 必填；可改；不唯一                                         |
| normalizedName | 字符串 1～200         | 服务端从 name 生成；客户端不可写                           |
| creditCode     | 可空 CHAR(18)         | 可选，默认 null；按 D-06 补录/纠正，非空不可清空           |
| ownerId        | User FK               | 服务端固定创建操作者；普通 PATCH 禁写，后续仅 T09 受控分配 |
| status         | ACTIVE / ARCHIVED     | 服务端默认 ACTIVE；普通 PATCH 禁写                         |
| description    | 可空纯文本，最多 2000 | 可选，默认 null；仅销售背景摘要，不存敏感凭据              |

不新增行业字典、客户等级、来源枚举、地址拆分、客户金额或“潜在/成交”人工标签。成交与订单事实由后续订单查询表达，不在客户上维护容易失真的第二套成交状态。协作者继续由既有 CustomerMember 候选关系表达，主负责人不重复存为协作者；其分配/上限/交接语义留 D-07，普通客户 DTO 不收 ownerId/collaboratorIds。

| 转换 / 动作                                           | 规则                                                                                                                            |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| ACTIVE → ARCHIVED，POST `/customers/:id/archive` | `customer:update` + 当前范围，expectedVersion、reason 1～500；客户下不得有进行中商机；有则 409，不批量自动关闭                  |
| ARCHIVED → ACTIVE，POST `/customers/:id/restore` | 同权限、expectedVersion、reason 1～500；允许恢复，不清除历史归档审计                                                            |
| ARCHIVED 时 CRM 写入                                  | 禁止客户资料 PATCH、联系人新增/修改/停用/设主、商机创建和跟进追加；先恢复。历史仍按当前范围可读；T09 受控交接不因归档被自动禁止 |

archive 与商机创建/阶段更新都锁同一客户行，避免“检查无进行中商机后又并发新增”。本次归档仅约束上述 CRM 操作；不改变报价/订单的有效性或财务交付状态，不给 D-01～05 增加隐含决定。T06/T07 不提前查询不存在的订单表或伪造阻断结果。

### 14.2.3 CustomerContact 最小字段与主联系人

| 字段            | 类型 / 长度          | 创建规则、默认与更新                        |
| --------------- | -------------------- | ------------------------------------------- |
| customerId      | Customer FK          | 只取路径，创建后不可改；错误父子链 404      |
| name            | 非空字符串 1～100    | 必填，可改                                  |
| title           | 可空字符串，最多 100 | 职务，可选，默认 null                       |
| phone           | 可空字符串，最多 40  | 格式按 D-06，可选，默认 null                |
| phoneNormalized | 可空字符串，最多 21  | 服务端派生，不可直接写                      |
| email           | 可空字符串，最多 254 | 格式按 D-06，可选，默认 null                |
| emailNormalized | 可空字符串，最多 254 | 服务端派生，不可直接写                      |
| status          | ACTIVE / INACTIVE    | 创建默认 ACTIVE；不能普通 PATCH，停用走动作 |
| isPrimary       | boolean              | 可选，默认 false；可通过创建或 PATCH 设置   |

每个有效联系人至少提供 phone/email 之一；不要求电话或邮箱唯一，允许同企业多人共用。每客户最多 100 个有效联系人，停用记录不占有效上限。停用不物理删除，历史姓名及归属仍可追溯；不对外承诺法定永久保留，个人信息清理另行受控决策。

主联系人采用“**零或一个有效主联系人**”：不自动把首位联系人设主；允许尚无联系人或尚未指定主联系人。设置某人为主时，在客户锁下自动清除旧主标记并设置新主，同事务完成；旧、新两行 version 都提升，成功审计记录关系变化。命令只需目标联系人 expectedVersion；选择主联系人的行为是替换选择，不能解释为保留旧主的条件更新。两个并发请求指定不同联系人时按客户锁顺序串行，后提交者成为主联系人，始终至多一个；UI 可 GET 刷新最后选择。

PATCH `isPrimary:false` 可清空当前主标记；停用主联系人时自动清主，不自动选其他联系人。POST `/customers/:id/contacts/:contactId/deactivate`，请求 `{expectedVersion,reason}`（1～500）；INACTIVE 不可编辑、不可设主，V1 不提供恢复或删除，误停用可创建新联系记录并在业务沟通中核实。普通 PATCH 仅允许 name/title/phone/email/isPrimary。

数据库保留 `is_primary`，采用“仅主联系人时生成 customer_id，否则 SQL NULL”的可空生成辅助列加 UNIQUE，并约束 INACTIVE 不得为主；具体 Prisma/生成列映射与受审查 SQL 在 T04 确定，本次不生成迁移。不能误用 UNIQUE(customer_id,is_primary)，否则会把普通联系人也限制为一个。客户锁仍负责自动切换和有效数量上限。该辅助列是局部唯一性实现，不是新业务实体或工作流。

### 14.2.5 商机阶段、赢单与输单

商机阶段仅用于销售管理：NEW=新线索；QUALIFIED=需求和客户意向已初步明确；NEGOTIATING=方案/商务沟通中。不要求填写概率，不使用可配置阶段引擎，不因阶段自动创建报价、订单或交付。

POST `/opportunities/:id/change-stage`，输入 `{expectedVersion,stage,reason}`，stage 只接受三个进行中枚举，reason 必填 1～500。允许进行中阶段之间前进或回退；不允许同阶段新命令无意义更新（409），有效同 Key 重放仍返回原结果。reason 写白名单业务审计摘要，不新增阶段历史表；正文敏感信息不入审计。

| 起点                          | 终点 / 命令           | 首次执行前置条件                                                                                       |
| ----------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------ |
| 任一进行中阶段                | 另一进行中阶段        | 当前父客户 ACTIVE、opportunity:update + 当前客户范围、版本匹配、说明必填                               |
| QUALIFIED / NEGOTIATING       | WON，既有 close-won   | 客户 ACTIVE；客户至少一个有效联系人；输入 reason 1～500，明确人工判断的赢单依据；其余权限/版本检查同上 |
| NEW                           | WON                   | 409：先完成需求确认并转 QUALIFIED；不能直接把未确认线索标赢单                                          |
| NEW / QUALIFIED / NEGOTIATING | LOST，既有 close-lost | 客户 ACTIVE；reason 1～500 必填，不要求已有联系人或报价                                                |
| WON / LOST                    | 任意阶段、普通编辑    | 拒绝；V1 不重开、不改标题/正文/责任人之外的业务内容；责任人受控交接仍留 T09                            |

**已批准的赢单含义**：销售认为客户已明确选择合作，是人工销售判断；不等于报价接受的法定证据、Order.CONFIRMED、到账或可启动交付。close-won 不要求已创建/接受报价或确认订单，因此不增加 T07 → T11/T16 的反向依赖。后续可以在 WON 商机继续报价/生成订单，相关合法性由 D-01～05 和对应命令决定；不能仅凭 WON 放行。LOST 不作为新报价/新订单来源；后续报价与订单接入时需同步这条业务前置，不追溯作废历史报价或订单。

若商机已有历史订单，仍允许销售标 LOST，原因必须表明本轮销售尝试终结；**不会取消订单、撤回审批或释放来源唯一性**。这避免 T07 查询未来订单表，也避免商机误标绕过 BR-005 等订单规则。若希望“有有效订单禁止 LOST”或“订单确认才算 WON”，应作为审核改动明确提出，会增加 T07 与订单阶段的后续联动验收；本次批准不采用。

终态误操作通过新建独立商机继续处理，旧记录保留，不自动复制报价/订单或复用接受证据。商机终态不改变父客户生命周期；只要仍有其他进行中商机，客户仍不可归档。

### 14.2.6 FollowUp 最小字段与追加规则

| 字段           | 类型 / 长度          | 创建规则、默认与更新                                                             |
| -------------- | -------------------- | -------------------------------------------------------------------------------- |
| opportunityId  | Opportunity FK       | 只取商机路径；不可改变；customer 从商机推导，不冗余存 customerId                 |
| authorId       | User FK              | 服务端当前操作者，保留停用历史，客户端不可写                                     |
| content        | 非空纯文本 1～4000   | 必填；不自动解析附件/富文本/外链                                                 |
| nextFollowUpAt | 可空 UTC DATETIME(3) | 可选，默认 null；RFC3339 UTC `Z`、毫秒精度；有值必须晚于本次首次执行的服务器时间 |
| correctionOfId | 可空同表 FK          | 可选，默认 null；仅用于指明本条在纠正同商机已有记录，不替换原文                  |

只通过现有 POST `/opportunities/:id/follow-ups` 新增；没有 PATCH/DELETE，也不给作者/管理员编辑历史的后门。误记通过追加更正，`correctionOfId` 必须属于同一可见商机；可纠正他人记录但作者仍是当前人，语义是说明，不是审批或作废原记录。该自引用只指向已有记录，不能指向自身/未来记录；历史记录仍全部显示，不自动折叠为“最新真相”。

进行中商机可新增一般跟进或更正，nextFollowUpAt 仅为人工计划备注；不建提醒任务、不修改旧记录的计划时间、不过期自动变更状态。WON/LOST 后允许追加一般说明或更正，但必须 `nextFollowUpAt=null`，不会重开商机。父客户 ARCHIVED 时不允许追加，先恢复客户。列表默认按通用倒序返回，不提供前端可编辑历史。

不要求传商机 expectedVersion：新增是独立追加操作，不修改商机内容或 version。服务端在客户→商机锁下重验当前状态；与 close-won/lost 竞争时，先提交追加可成功，后终结；先终结则按终态规则拒绝携带未来计划的追加。相同 Key 重放不重新检查时间已过而拒绝旧成功结果。

### 14.2.7 API、权限、锁与异常影响

新增的查重、归档/恢复、联系人停用、商机阶段变更均是**已批准、待实现契约**，现有路由仍按 API 设计保留；未实现不得注册 OpenAPI 路由。联系人正文只出现在受权限控制的 GET，写响应/幂等只存标量摘要。

| 操作                                    | 权限与对象范围                                             | 对应实施任务 |
| --------------------------------------- | ---------------------------------------------------------- | ------------ |
| 客户列表/详情/联系人读取、查重          | customer:read；SELF_COLLABORATOR / TEAM / ALL 按同条 grant | T05/T06      |
| 客户创建                                | customer:create，owner=actor；无客户端指派                 | T06          |
| 客户资料、归档/恢复、联系人写/停用/设主 | customer:update + 当前客户范围                             | T06          |
| 商机创建                                | opportunity:create + 当前父客户范围                        | T07          |
| 商机读取/跟进列表                       | opportunity:read + 当前父客户范围                          | T07          |
| 商机编辑/阶段转换/终结、跟进追加        | opportunity:update + 当前父客户范围                        | T07          |

角色名、商机 owner、跟进作者、联系人创建人均不构成额外授权；管理员无默认业务旁路；T09 分配仍用 customer:assign 等既有边界，不由本文定案 D-07。缺失的 M2 关联 scope 继续拒绝。

事务沿用既有组件：幂等 Key → 全体相关用户 → 角色 → 部门 → 客户 → 已有订单（仅真正涉及订单时）→ 子记录。CRM 子记录如需同时锁多类，固定 Opportunity → CustomerContact → FollowUp，各类 ID 升序；单一操作不锁无关记录。T05 需将其写回完整锁等级并实库验证，不把此草案当成已验证协议。客户归档、商机创建/终结、联系人上限/设主都先锁客户以串行化相应不变量。T07 无需造订单表或订单锁占位。

| 异常                                                                             | HTTP / code             | 输出与优先级                                     |
| -------------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------ |
| 缺失/过期/停用身份                                                               | 401 UNAUTHENTICATED          | 无业务详情                                       |
| 无动作 grant                                                                     | 403 PERMISSION_DENIED        | 不继续查询对象状态                               |
| 不可见/不存在、联系人或更正记录父子错配                                          | 404 RESOURCE_NOT_FOUND       | 不暴露真实父 ID 或版本                           |
| 字段、长度、枚举、格式、未知字段、null 类型不合法                                | 400 VALIDATION_FAILED        | 仅安全字段名与规则，不回显联系人正文             |
| expectedVersion 不匹配                                                           | 409 VERSION_CONFLICT         | 仅在当前授权通过后返回，不泄漏不可见对象版本     |
| 信用代码冲突、归档禁写、终态改写、缺赢单联系人、同阶段转换、上限或计划时间不满足 | 409 BUSINESS_RULE_VIOLATION  | 信用代码用统一消息；其他只返回可见目标的安全原因 |
| Key 冲突/处理中/提交未知、审计故障                                               | 既有 409/503 及现行专用 code | 沿用 ADR-003/005，不新增绕过或吞错逻辑           |

新动作不滥用订单专用状态码。无 PATCH/DELETE 路由的跟进修改/删除请求不得改变数据，HTTP 行为按框架未注册路由统一返回 404；不能用“作者本人”放行。
