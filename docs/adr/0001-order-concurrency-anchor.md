# ADR-001：订单作为跨模块并发协调锚点

- 状态：Accepted（项目内部设计基线，待实现验证）
- 日期：2026-10-29
- 关联：BR-005、BR-008；requirements.md §4、INV-004、INV-005（原 BR-012～016 为无效引用，2026-10-29 修正）

## 背景
取消订单、启动交付、批准订单变更和结项操作跨越不同业务模块。只在各自 Service 中分别检查数据，可能导致两个事务均通过预检查，最终出现“已取消且已启动交付”或“已完成却存在新增未验收范围”的矛盾。

## 决策
系统采用单个 MySQL/InnoDB 数据库及模块化单体。**以 `orders` 当前订单行作为共享并发协调锚点**；所有会改变订单有效性、交付是否可启动、有效交付范围或订单结项条件的命令，均须在同一个数据库事务中取得该行的并发控制资格，并在受保护的事务中再次检查相关状态。

实现方式可以是先 `SELECT ... FOR UPDATE` 锁定订单行（由适当的数据库访问机制执行）后检查相关记录，或者采用对订单行的受条件约束的版本更新，并让全部竞争命令遵循相同协议。**条件更新并不替代跨表条件的事务内重检**。选型需通过 MySQL 集成测试明确验证；Prisma 客户端若不直接暴露特定锁操作，应在封装层使用受控的参数化 SQL，并审查版本兼容性。

订单仍处于 `CONFIRMED` 时，交付项目可以独立转为 `IN_PROGRESS`；绝不为获取互斥而将 `Order.status` 改成 `DELIVERING`。在启动交付之前还需核验首付款或有效豁免、待审批取消申请等阻断条件。任何参与方不得绕过这套协调协议直接写入关键数据。

## 事务顺序（概念级）
1. 开启事务，获取指定订单行的独占协调资格；所有竞争命令使用一致的锁顺序。
2. 事务内查询并确认订单主状态、交付曾否启动、待处理冲突申请、付款或豁免条件、当前有效范围版本等相关约束。
3. 业务条件满足时，更新对应业务实体；仅在订单真正取消时写 `orders.status=CANCELLED`，仅在交付启动时写交付项目状态。
4. 同一事务写入关键成功审计与审批结果，提交。失败则回滚所有业务写入；数据库死锁/超时应明确处理，安全的可重试命令结合 ADR-005（替代 ADR-002）。
5. 竞争丢失不等于“审批人驳回”。取消与启动等关键竞争命令按 ADR-003 预先持久化尝试、回滚后独立记录失败；进程中断留下 UNKNOWN 待核对，不伪造确定失败。申请如何标记失效由专门业务命令另行提交，不能伪造审批意见。

## 保持的不变量
- 订单 `CANCELLED` 与“交付曾实际启动”不能同时成立；交付被暂停并不消除启动事实。
- 有有效待审批取消申请时不能新启动交付（已采用的业务政策）。
- 基于过期交付范围的结项不得成功；有效范围变更与结项共用订单协调机制。
- `COMPLETED` 的历史订单不得被一般编辑操作悄悄回退；新服务另走正式流程。

## 备选方案及取舍
- 各 Service 分别事务：简单，但无法保证跨模块不变量，拒绝。
- 独立 `order_locks` 表：可用，但多维护一张锁表且无明显收益，当前不采用。
- 全部使用全局 SERIALIZABLE：隔离强、开销与死锁处理复杂，不作为默认替代方案。
- 分布式锁（Redis）：对单 MySQL 的业务状态一致性不是必要条件，且不能替代数据库提交原子性。

## 代价与风险
同一订单的关键操作将串行化；必须统一访问协议、缩短事务时长，避免事务内调用外部服务；需要死锁重试策略和锁等待监测。

## 验证 / 验收
- 并发启动交付和取消获批，最终只能产生一个有效结果。
- 启动成功后，订单保持 `CONFIRMED`，交付为 `IN_PROGRESS`；取消不能生效。
- 取消成功后，不能启动交付。
- 完成订单与新增已批准交付范围并发，不能留下已完成但存在未验收义务的结果。
- 模拟死锁和回滚，确保没有部分写入或错误的“已驳回”审计。

## 影响范围
Order / OrderChange / Delivery / Cancellation / Acceptance Service；M1～M3 实现后必须验收。

## 分阶段接入（DC-012）

M1 建立共同订单事务入口及固定锁顺序；M2 前置阻断申请表/查询（即使暂未开放申请 API），真实查询不能以固定 false 或空实现代替。付款条款、范围和验收模型分别受 DC-005/004 的开发门禁约束。M3 所有会改变阻断条件的申请创建、撤回、拒绝、失效、变更生效均经该入口先锁 orders，再读写申请；不得出现模块本地旁路。

授权与归属的写入锁顺序先遵循 permission-matrix.md §4.2，再进入订单及其子记录；授权管理、移交与业务命令共用该顺序。M3 接入前重跑 M1/M2 权限及并发回归，包括申请创建 vs 启动/结项、取消批准 vs 启动、范围生效 vs 结项、验收有效性变化 vs 结项；失败/死锁不产生部分写入。
