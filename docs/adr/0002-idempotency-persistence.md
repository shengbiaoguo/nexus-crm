# ADR-002：关键业务命令使用 MySQL 持久化幂等记录

- 状态：Superseded by [ADR-005](0005-idempotency-scope-clarification.md)（2026-10-29）
- 日期：2026-10-29
- 关联：INV-006、审批 / 收款 / 冲正接口

## 背景
> 本文保留历史设计与取舍，不再作为当前契约。原“操作参与 scope”与验收“同 Key 不同操作冲突”不一致；现行规则以 ADR-005 为准，单企业 scope 固定为 user ID，操作进入请求指纹。

客户端可能因超时重试；请求也可能同时重复到达。仅按订单状态做条件更新可以阻止重复改变业务状态，却不能区分“首次成功但响应丢失”与新的命令，更不能可靠重放结果。

## 决策
对审批、创建订单、确认收款、冲正等有不可重复副作用的 POST 命令要求客户端提供 `Idempotency-Key`。服务端以**认证主体或租户作用域 + 路由业务命令类型 + Key** 定义唯一性作用域，保存对目标 ID、操作类型及规范化参数计算的请求哈希；相同 Key 不同语义必须返回冲突，而非错误重用成功结果。

核心业务数据变更、审批/收款审计与最终的幂等结果必须在**同一个 MySQL 事务**中提交。`idempotency_records` 由数据库唯一约束保证同一个作用域内只有一个所有者；并发重复请求不得第二次执行副作用。

## 处理规则
- 首个请求获取 Key 所有权，完成验证与业务事务，提交最终业务效果以及可重放响应信息。
- Key + 请求指纹一致，且已完成：按 API 契约返回首次结果；前端可随后 GET 最新订单状态。
- Key 相同但指纹不同：返回 `409 IDEMPOTENCY_KEY_REUSED`。
- 重复请求在首次请求仍进行时：等待受控时限或者返回可重试的“处理中”响应；不能冒充成功。
- 业务失败可区分确定性最终失败与技术性暂态失败；禁止无条件缓存所有异常。
- `PROCESSING` 表示处理中但不保证已落盘；**若将 PROCESSING 先独立提交**，则必须另外实现超时租约、恢复与接管机制。V1 优先采用单数据库事务及唯一键竞争，避免产生无法恢复的长期处理中记录。
- 幂等保留期属于公开 API 契约（暂定关键审批 7 天，实际需业务确认）；过期后安全性依赖业务唯一约束与状态机，不承诺无限期重放。

## 备选方案
- Redis SETNX：速度快但与 MySQL 提交不原子，不作为最终权威。
- 仅状态机 / 乐观锁：避免一部分重复写，但不能重放首次响应。
- 仅前端禁用按钮：网络重试和直接 API 调用仍会发生。

## Schema 关联
现有 `IdempotencyRecord(scope,key,requestHash,status,httpStatus,responseBody,expiresAt)` 是基础草案。后续实现需明确 `scope` 组成、保留期清理策略、结果大小限制、敏感数据脱敏、失败语义和事务封装；当前 M0 Schema 本身不表示幂等已经生效。

## 验收
- 两个相同 Key 同时提交，至多一次业务副作用。
- 首次提交成功但丢失 HTTP 响应，重试可得到成功结果。
- 相同 Key 不同操作返回 409。
- 事务提交前模拟崩溃，不出现“业务完成但没有最终幂等记录”的状态。
- 不同 Key 对已处理订单的新审批命令受到状态机规则约束。
