# ADR-004：数据库版本演进采用 Prisma Migration

- 状态：Accepted（设计基线，待本地执行验证）
- 日期：2026-10-29
- 技术：MySQL 8.4 / Prisma 7（精确版本以锁文件为准）

## 背景
手工修改开发、测试、生产库容易产生 schema 漂移，不能可靠审查、回溯和复现。数据库结构变化应当像代码一样受到版本控制。

## 决策
数据库 schema 以 `schema.prisma` 与已审查、已提交 Git 的 `prisma/migrations/**/migration.sql` 共同维护；应用代码与迁移脚本在同一变更中评审。开发环境由 `prisma migrate dev` 生成迁移、更新本地库；生产发布执行 `prisma migrate deploy`，不使用 `migrate dev` 或未经审查的 `db push` 修改生产库。

必须审查生成的 DDL、索引、外键、已有数据约束及锁表风险；数据库部署前做备份并在相似数据量的环境验证。**迁移 SQL 不自动等于安全变更**。

## 变更流程
1. 提需求 / 设计变更，确定是否存在数据兼容性问题。
2. 修改 Prisma Schema，开发环境生成带有明确名称的 Migration。
3. 审查 `migration.sql`，补充必要的可重复执行的数据回填工具/脚本及数据核对查询。
4. 在全新数据库和含历史数据的预发布数据库分别执行迁移，并跑集成测试。
5. 生产先备份；按兼容顺序部署迁移与应用，保留执行记录并核验。
6. 出现失败时优先按恢复预案止损；**Prisma 没有通用自动 down migration**，不能简单承诺自动回滚已经生效的数据破坏变更。

## 兼容性方案（Expand → Backfill → Contract）
以新增 `customers.industry` 为例：
- Expand：先添加允许 NULL 的字段，新旧应用均可正常工作。
- Backfill：分批填充历史数据，验证覆盖率与数据质量；必要时双写/双读过渡。
- Contract：应用切换并完成核验后，下一次独立迁移添加非空约束或移除旧字段。
在大表上尤其要评估 DDL 锁与在线迁移方案。

## 限制及异常
- `migrate deploy` 不会自动生成新迁移，也不会修复生产漂移。
- 出现失败迁移时，先定位 `_prisma_migrations` 状态并按官方恢复流程处理；禁止未经评估直接清空迁移历史。
- 数据备份恢复、前向修复与应用版本回退是不同手段，需要明确发布计划。
- 生产数据库不允许直接手工 `ALTER TABLE`；紧急修复必须形成补录迁移和事件记录。

## 本项目初始状态
Starter 中 M0 `schema.prisma` 已编写，但因当前环境未运行 MySQL/Prisma CLI，**首份 Migration 尚未生成/验证**。本地第一次 `migrate dev` 后必须把真实生成的 SQL 提交版本库，执行审查与测试后才宣称 M0 完成。

## 验收
- 空库能够通过迁移完整构建。
- 包含历史数据的库能完成新增字段与回填，无数据丢失。
- CI 能核查 schema / migration 一致性和集成测试。
- 线上部署不用 `db push`，保留可追踪迁移记录与备份。
