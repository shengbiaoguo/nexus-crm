# ADR-003：业务审计与运行日志分离

- 状态：Accepted（设计基线，待实现验证）
- 日期：2026-10-29

## 背景
CRM 的订单审批、客户归属、收款确认和冲正需要可追溯业务事实；HTTP 错误、数据库慢查询与服务崩溃属于技术运维事件。将两者混用，可能导致业务日志随轮转丢失或在事务失败时记录虚假的成功事实。

## 决策
建立两条日志通道：
1. **业务审计 AuditLog（MySQL）**：记录操作者、操作类型、业务对象、请求关联 ID、时间、必要的前后变化摘要与审批依据。成功业务状态变更的审计行与业务写入**同事务提交**。
2. **运行/安全日志（结构化 JSON）**：记录 requestId、traceId（如适用）、耗时、错误码、服务/模块、告警等，按部署环境采集保留。普通 DTO 拒绝、未授权请求和技术错误采用尽力而为日志；以下关键尝试必须持久化，不以日志采集代替。

## 关键尝试可靠性补充（2026-10-29，DC-009）

本节补充两通道的可靠性，不推翻成功审计同事务原则。对订单审批决定、取消/终止批准、启动、结项、变更生效、收款确认/冲正、退款批准/实际退款登记及业务授权变更，在认证、DTO 和对象授权通过后、业务事务开始前，以独立短事务写 `command_attempts`：attempt_id、actor_id、operation_id、entity_type/id、request_id、idempotency_scope/key、request_hash、status=STARTED、started_at、finished_at、error_code、result_ref。禁止保存原始敏感请求体。

- 预写失败：不执行业务，返回 `503 AUDIT_UNAVAILABLE` 并触发运维告警；数据库不可用时不能承诺告警本身一定送达。
- 成功：业务事务同时提交 AuditLog、幂等结果和该 attempt 的 SUCCEEDED/result_ref。有效幂等重放仅结束本次 attempt 为 REPLAYED，不重复成功审计或业务事实。
- 确定回滚：回滚完成后用独立短事务将 attempt 置 FAILED/error_code，再返回原业务错误。该写入失败则返回 `503 AUDIT_UNAVAILABLE`，保留 STARTED 并告警，不能宣称已完整记录确定失败。
- 进程中断或 COMMIT 结果不明：持久化的 STARTED 是尝试存在的证据，不是业务失败的证据。定时核对超时记录（默认 5 分钟）并标 UNKNOWN；与原业务事务竞争更新时重新读取，不能覆盖已提交的 SUCCEEDED。根据幂等完成记录/成功审计关联核实；无法核实保持 UNKNOWN，人工核对，禁止自动重执行业务或伪造驳回。
- attempt_id 唯一；同 Key 的每次 HTTP 尝试可有各自 attempt，状态更新条件受控、不可覆盖成功。后台核对早于幂等结果清理，UNKNOWN/STARTED 不按完成记录的保留期删除；未知结果不能因 Key 清理变成可自动重试。

这保证崩溃前已有持久尝试线索，并明确无法确定最终结果的窗口；不承诺进程在任意时刻退出仍能立即记录准确失败原因。申请失效属于另一个受授权业务命令，不由失败审计自动改变。记录保留期限沿用待确认的审计保留政策，不引入消息系统。

## 保护措施
- 严禁在日志记录密码、访问令牌、完整银行卡号或不必要的敏感联系人信息；JSON 前后快照必须按允许字段白名单脱敏，并控制数据体积。
- AuditLog 仅允许通过专用服务写入；一般业务接口不提供修改或删除审计行能力。数据库权限与备份策略也要相应限制。它是应用级不可修改约定，**不等于法律意义上的防篡改存证**。
- 账号停用后历史 `actorId` 仍可追溯，不级联删除；系统操作使用明确主体标识，不能把未知主体冒充普通用户。
- 业务审计留存期限、个人信息删除/匿名化政策和审计访问权限应由具体客户与合规需求确定，不能默认无限期保留。
- 需要告警的重要事件：批量权限调整、管理员登录异常、大额冲正、审批失败率升高、审计写入故障。

## 备选方案
- 全写文件日志：缺乏关系查询和业务事务一致性，拒绝。
- 全写数据库：技术日志量大且易污染业务库，拒绝。
- 外部集中审计产品：后续合规升级可接入；V1 不强制。

## 验收
- 成功审批产生一条可关联的审计记录；审批事务回滚则不产生“审批成功”审计。
- 无权限访问记录为安全事件，但不伪造业务成功。
- 日志不包含凭据与高敏感字段；`requestId` 可串联 HTTP 请求及业务记录。
- 注入预写失败、业务回滚后退出、失败状态写入失败、COMMIT 结果未知，分别验证不执行/保留 STARTED 或 UNKNOWN、不伪造成功/驳回；核对任务不覆盖真实成功。

## 与现有 Schema 的差距
AuditLog 保存成功业务事实，并增加 attempt_id 可空关联（适用关键命令必须填写）；关键失败使用上述 command_attempts，不混入成功审计。M0 前置该表及核对任务基础设施；不因此宣称满足完整审计合规。
